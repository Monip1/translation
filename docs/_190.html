Updated instructions: We have updated design document, process journal, PR, code review, and presentation instructions, and the rubric. Please check out the tabs under Assignment 3 in the left navigation bar.

Collaboration: Continue using the driver/navigator pair programming approach from A2. The driver operates the development environment, interacts with the agent, and makes commits. The navigator helps guide the work and reviews proposed changes, design decisions, and test results. Both partners must act in both roles and spend roughly equal time as driver and navigator. Record the driver and navigator for each work session in your process journal so their roles can be matched to commit authors. Both partners remain responsible for understanding and verifying the implementation, including code generated by the agent.

Agentic Development: Use Codex or any other agentic tools (for example, Claude Code) to help explore the codebase, plan changes, implement the feature, and develop tests. You must work with the agent to discover edge cases and make design decisions, rather than letting the agent make all the decisions. Consider using skills like grill me to help with this process. You should review the changes it proposes and verify that they satisfy the requirements and fit the existing codebase. Both partners should be able to explain the submitted code.

You own everything your agent produces. Anything the agent writes for you is your work, and we grade it to the same standard as work you wrote by hand. Taking ownership means you:

  • Design decisions: Understand every decision in your design, whether you or the agent proposed it. Be able to explain the options and why you chose this one.
  • Code: Read and understand every line you commit. If you cannot explain it, do not submit it.
  • Tests: Check that the tests the agent writes test the right behavior, cover the edge cases, and can fail. A passing test is not enough.
  • Documents: Check that your design document, diagrams, journal, and pull request description are accurate and match what you actually built. The agent can write a polished explanation of something you did not do.
  • Mistakes: If the agent gets something wrong and you submit it, the mistake is yours.

Both partners are responsible for all of it. In your presentation and Q&A, either partner may be asked about any part of the work, including the parts the agent wrote.

Part 2: Translate Column in OpenRefine

Motivation

This assignment is inspired by Yelp-style restaurant reviews. Imagine analyzing a dataset of reviews written by diners in different languages. You want to compare their experiences and understand feedback about the restaurants, but the language differences make it difficult to work with the reviews together. Translating them into a common language can make the dataset easier to explore and analyze while preserving the original text for reference.

In this assignment, you will extend OpenRefine so users can translate an existing text column into a new column. You will practice working across an unfamiliar codebase, integrating an external service, handling failures, and testing a complete user-facing feature.

You will use Codex (or another agentic tool of your choice, such as Claude Code) as part of your development process. You are responsible for understanding, evaluating, and verifying the changes you submit. In practice, this means three things:

  • Understanding: You can explain what each change does, why it is needed, and how it fits into the rest of OpenRefine, without asking the agent.
  • Evaluating: You judge the agent’s suggestions instead of accepting them by default. Ask whether the approach follows the codebase’s conventions, whether a simpler option exists, and whether it handles failures and edge cases.
  • Verifying: You check that the work is correct by running it. Run the tests, try the feature in OpenRefine yourself, and test the cases you expect to break. Do not trust the agent’s claim that something works.

Task

Add a feature that lets a user select an existing text column, choose a target language, and create a new column containing the translated text.

For example, a project containing Yelp-style reviews may include reviewer names or IDs, restaurant names, and multilingual review text. A user should be able to translate the reviews into a chosen language and see the translations alongside the original data.

You choose which languages to support and how many. Every pair must support at least these three languages, each as both a source and a target: English, Spanish, and Mandarin Chinese. Beyond that, the sky is the limit. Add as many languages as you like, for example Telugu, Tamil, Hindi, or French. For reference, our own solution supports five: Spanish, Mandarin Chinese, English, Telugu, and Tamil. Treat that as one example, not a target. Document your supported languages in design.md and explain how someone would add another one.

The images below show the result we expect: the original column stays as it is, and a new column with the translated text appears next to it. They do not show a required design. You do not need to match their layout, buttons, or wording.

You decide how the feature works in the interface and how it fits into OpenRefine. For example, you decide:

  • Where the user starts the operation.
  • How the user chooses the column and the target language.
  • What the user sees while translation is running, and when something goes wrong.
  • How the new column is named and where it is placed.

Look at how existing OpenRefine features handle these questions, and follow the codebase’s conventions. Explain your choices and the alternatives you considered in design.md.

Required features

  • Translation: You decide how the translation is done. You can call a hosted translation API, or you can run a translation server or model locally. Either way, it must support at least the three required languages (English, Spanish, and Mandarin Chinese) as both source and target languages, plus any extra languages you choose to support. Compare the options and choose one. Think about cost, usage limits, setup effort, speed, translation quality, and how easily someone else can run your code. Explain your choice in design.md, and document the setup steps, configuration, and any usage limits. Keep credentials out of committed files. You should not be spending any money on translation.
  • New column and data preservation: Place each translation in the row corresponding to its original text. Preserve the source column, other existing data, and row order. Do not overwrite an existing column without warning.
  • OpenRefine integration: Integrate the feature with the frontend and backend using the codebase’s existing conventions.
  • Dataset: Find a Yelp reviews dataset online, or generate your own Yelp-style reviews, for testing purposes. You may choose any dataset as long as it contains a column for text reviews. Commit a small sample of about 20 rows to the Assignment3/ folder so anyone running your feature (for example, tutors while grading your final PR) can try it. The sample should include reviews in every language you support, so a grader can test each one.
  • Edge cases and design decisions: Identify edge cases and document your chosen behavior (e.g., failure handling, translated text in the same language, etc). Explain decisions that affect the user experience in design.md.
  • Testing: Run the relevant existing tests, and add new tests that cover your feature’s normal behavior, the edge cases you chose to support, and failure handling. If your changes break an existing test, work out why. Change the test only if the expected behavior has intentionally changed. Do not delete or disable failing tests. All relevant existing tests and your new tests should pass in your final submission.

Submission

Review this table for assignment deadlines.

For the initial PR submission, create a folder called Assignment3 at the root of your repository. In this folder, add your process journal (journal.md), your design document (design.md), your exported agent chat history (see Exporting your chat history), and your sample dataset of about 20 rows. The instructions are on the A3 Process Journal and Design Document pages. Then open a pull request, but do not merge it. Use the A3 pull request template.

This is one pull request for the whole assignment. After the code review, you push new commits to the same assignment3 branch, and the pull request updates itself. The “final PR” deadline is the deadline for those commits.

Open the pull request in your pair’s repository, with main as the base branch and assignment3 as the compare branch. Do not open a pull request against the course template repository or against OpenRefine/OpenRefine.

Document how to run OpenRefine with your changes, so someone else (for example, tutors while grading your final PR) can follow the steps without asking you. In your pull request description, include any server setup, your translation setup (a hosted API or a local server), and how to try the feature with your sample dataset. If your feature needs an API key, explain how someone can get their own key and where to put it. Never share your own keys or other secrets. Your reviewers do not have to set up or run your feature. They review your code, tests, documents, and the screenshots and videos in your pull request.

After the initial PR submission deadline, each student will be assigned to review another pair’s submission, so your pair will review two other pairs’ submissions in total. Instructions can be found on the A3 Code Review page. Your tutor will post the GitHub usernames of the code review assignments and you will be added to the appropriate repositories as Readers so you can provide your review.

Using that feedback, fix your initial PR as necessary, adding new commits to the assignment3 branch. You will also prepare a ~10 minute presentation about your submission for team meetings, followed by ~10 minutes of Q&A with your tutor (20 minutes total). The tutor will ask you questions about your design, code, tests, and documents. The presentation will be graded on how you communicate your implementation and design decisions, not the technical excellence of the implementation itself. Use the A3 presentation page for the plan, tips, and details on how the Q&A works, with example questions.

Each student is graded separately for collaboration and communication, so partners may receive different scores in those categories. The technical score is the same for both partners if both have contributed satisfactorily to the technical work; otherwise, technical scores may differ. See the A3 Rubric for the grading rubric used for this assignment.

Exporting your chat history

Save your full conversation with the agent in the Assignment3/ folder. We will check your chat history against your process journal and design document, so they should match. Include every session you used for this assignment, not just the last one. If you used more than one session, add one file per session and name them so the order is clear (for example chat-1.md, chat-2.md).

Claude Code: In the session, run /export session.md. This saves the conversation as plain text to that file. If you run /export with no filename, a dialog lets you copy to the clipboard or save to a file. See the Claude Code commands reference.

Codex: In the session, run /export session.md. This saves the complete conversation as Markdown to that file. If you run /export with no filename, choose Save to file (or Copy to clipboard and paste it into a file). Wait for the current turn to finish before exporting. See the Codex commands reference.

Export before you close each session, and move or save the file into Assignment3/.

Other tools: Look up how your tool saves or exports conversations. If it cannot export, copy the conversation from your terminal or app into a text file.

Before you commit, search your chat history for API keys, tokens, and passwords, and remove them. Do not edit anything else. We want the real conversation, including mistakes and dead ends.
